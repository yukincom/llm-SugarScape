# 2026-10-23 座標・視界計算のRust移行

## 移行した責務

既存の`Environment.relative`、`LLMAgent.get_local_view`、`Simulation._in_view_range`、絶対移動の一意性判定、`cardinal_destinations`が使うトーラス計算を、`rust-core/src/lib.rs`にまとめた。API・CLI・画面は同じコアを使用する。従来のPython計算実装は製品から削除した。

Rustは外部crate依存なしのcdylib。Pythonはctypesの配列ABIを通して座標を渡し、視界内の入力indexと相対座標を一括で受け取る。自己・死亡個体の選別、資源の辞書順、他者の入力順、MBTI・メッセージの文字列表現は従来どおり維持する。不可視個体の属性を返す新しい観測経路は設けない。

PythonとNumPyの乱数・状態遷移・プロンプト整形・Unicode応答解析・保存処理・Streamlit/pywebview/描画はPythonに残す。これらはライブラリや抽選順、既存ファイル形式の契約を持ち、今回の数値計算移行とは独立して検証すべき範囲である。

## 数値・境界条件

- 負方向の周回に`rem_euclid`を使用し、偶数サイズの半周を負方向にする既存仕様を保つ。
- 加減算はi128で行い、i64引数の端でも中間オーバーフローを避ける。製品の盤面サイズ範囲は変更しない。
- 視界と通信は正方形の範囲判定。盤面全体を超える任意長整数の半径は、同じ結果になる最大距離へ上限化してFFIへ渡す。
- サイズ1/2で絶対目的地から方向が一意に決まらない場合は、従来どおり補正しない。
- 隣接候補は`+x,-x,+y,-y`順で重複を除く。斜め移動の再要求では指定方向へ向かう候補だけを残す。
- ABIはバージョン1。null、長さ、サイズ、配列長のオーバーフローを検査し、所有権を言語間で移転しない。Pythonが所有する整列済み・重複しない配列を呼出し中保持する。

## ビルドと記録

Rust 1.99.1を`rust-toolchain.toml`で固定し、Cargo.lockを追跡する。`tools/build_native.py`は`--locked --offline`でビルドする。新しいcrateやTLSスタックの導入はない。今回のローカル構築では既存のRust 1.99.1を読み取り利用し、ツールチェーンの重複導入はしていない。

`native/build.json`へABI、コンパイラ版、Rustソース・バイナリのSHA-256を保存する。起動時に照合し、欠落・古いコア・別アーキテクチャ・ABI不一致では再構築を案内する。旧Pythonコードへの暗黙フォールバックはない。実験のprovenanceにもRustのソースと構築情報を含める。

py2appは通常、data_files内のdylibもstrip・再署名する。そのままでは構築時のハッシュが変わるため、処理後に検証済み・署名済みのRustバイナリとmanifestを戻し、最後にアプリのルートだけを署名する。ネストしたコードを含む厳密な署名検証と、同梱PythonによるRustコアの実行・ソース照合を通してからZIPを作る。

## Pytraの評価

[Pytra](https://github.com/yaneurao/Pytra)は共有の`/Applications/Pytra`、commit `9f341e04fefd8eacac1081c59e80f4042ee80a6f`を読み取り利用した。clone・二重ダウンロード・共有ソースの編集は行っていない。

固定版の実CLIは`-build INPUT.py --target rs --rs-package --opt-level 0 -o OUT`。加算と座標計算の2入力を変換し、各生成packageの全Rustファイル・Cargo.toml（計4,418行）をレビューした。元の`response_fields.py`はキーワード専用引数の`*`で変換を完了できなかった。

生成packageはRust 1.99.1によるオフラインビルドで、未生成の`pytra_built_in_error`・`pytra_std_re`参照によるE0432を確認した。生成された座標関数だけを無変更で抽出して実行すると、`origin=9,target=0,size=10`がPythonの`1`に対して`-9`になった。その他、負数除算、Unicodeのバイトoffset、リスト共有、I/Oエラー処理にも既存契約との差があり、今回の製品には生成物・runtimeを採用しない。既存MITソースの計算仕様から小さいRust実装を手動で作成した。

## 同等性と性能

移行前の公開ソース`e81e4d2`と同じ計算実装から、5盤面サイズ（1/2/10/11/30）×2シードについて、初期状態＋20ターンの全snapshot・event・プロンプト・Python/NumPy RNG stateを固定した。`tests/fixtures/geometry-before-rust.json`へ計210時点のSHA-256と最終集計を保存し、Rust移行後と全件一致した。乱数生成器自体は移行していない。

さらに、16,000座標組の相対座標と視界、サイズ1〜8の隣接候補と絶対移動、半周・負座標・巨大半径・不可視/死亡個体の除外、欠落バイナリとABIの異常系を検証する。既存の観測・Current Step・応答補完・凍結観測のテストも維持する。

同じ入力を100回ずつ処理したFFI込みlocal view生成の中央値は、3個体/21資源でPython 27.9µs → Rust 27.0µs、60個体/600資源で18.67ms → 15.10msだった。単一環境の計測であり、LLM生成時間やアプリ全体の高速化を示す値ではない。

最終検証ではPython全241テスト、Rust 2テスト、pip checkが成功した。Macアプリを再構築し、同梱PythonだけでMock 2実験（計18判断、8盤面画像）、CSV集計2行、隔離したローカルHTTP接続・4判断・4件の翻訳保存・3盤面画像を確認した。HTTPは固定応答のテストサーバーであり、実LLMの評価ではない。

実際のpreview.38ウインドウからもMock 3個体×5ターンを実行し、15判断・6盤面画像・統計・初期/各ターンの盤面表示を確認した。アプリ終了後に専用サーバーの終了と厳密な署名検証を確認した。既存8080サーバーの停止・再起動・モデル変更は行っていない。
